# Структура единого хранилища знаний для разных нейросетей

**Вывод: предлагаю четыре изолированных Git-репозитория и одну папку `1_LLM` на Google Drive с тремя зонами: карта системы, проверенные пакеты для моделей и шифрованные резервные копии.** Рабочим источником остаётся Git, задачами управляет трекер, а Drive не становится ни общим редактируемым промптом, ни двусторонней синхронизацией между компьютерами.

> **Нужно от тебя:** согласовать эту структуру. После твоего «согласовано» следующий шаг - создать пустую структуру в Drive, настроить rclone на тестовом безопасном комплекте и доказать восстановление. До этого содержимое Drive и настройки доступа не меняются.

Дата проекта: 27.11.2026. Статус: предложение для согласования, не внедрённая система. Этот документ дополняет [общую архитектуру от 25.11.2026](https://tema-mail.github.io/razbory/universalnye-pravila-ii-863039de/). Ссылка и ID папки Drive сохранены в приватном состоянии проекта и намеренно не публикуются здесь.

## 1. У каждого типа данных будет один источник истины

Система разделена на четыре независимых контура. Это исключает главные риски исходной задачи: устаревшие копии правил, смешение личного и рабочего, конфликты между компьютерами и резерв, который невозможно восстановить.

| Контур | Источник истины | Что попадает в Drive | Что запрещено |
|---|---|---|---|
| Правила и знания | Приватные Git-репозитории | Версионные экспорты и шифрованные снимки | Редактировать рабочие правила только в Drive |
| Задачи | Выбранный трекер, по умолчанию GitHub Projects | Только зашифрованные технические сводки | Вести второй параллельный список задач в Markdown |
| Секреты | Менеджер секретов и офлайн-хранилище восстановления | Ничего в открытом виде | Помещать OAuth, cookies, `.env`, пароли и ключи в Git или Drive |
| Технические журналы | Репозиторий операций или защищённое хранилище запусков | Датированные отчёты и heartbeat | Считать текстовый отчёт доказательством без данных проверки |

Общая схема:

```text
                    Люди и нейросети
                           |
                           v
                Единый вход AGENTS.md
                           |
             +-------------+-------------+
             |                           |
       Git-репозитории               Трекер задач
       правила и контекст            статусы и сроки
             |                           |
             +-------------+-------------+
                           |
                 Проверки и сборщик
                           |
             +-------------+-------------+
             |                           |
      Адаптеры на устройствах      Экспорт и резерв
      Kimi / Codex / Claude        в Google Drive 1_LLM
      Gemini / веб-пакеты
```

Синхронизация не является одним потоком «всё со всеми». Есть три разных процесса: распространение правил через Git, передача результата сессии через проектные документы и одностороннее резервное копирование в Drive.

## 2. Четыре репозитория разделяют правила и права доступа

Предлагаемая локальная структура после внедрения:

```text
~/AI-OS/
├── core/                       # репозиторий ai-core
├── personal/                   # репозиторий ai-personal
├── studio-private/             # репозиторий studio-private
├── studio-team/                # репозиторий studio-team
└── projects/                   # клоны отдельных проектов по мере необходимости
```

Это новые адреса проектируемой системы, а не существующие папки. Текущая рабочая папка `~/Documents/Kimi.ai` сохраняется как место ведения состояния переезда. Автоматически переносить или переименовывать её не требуется.

### 2.1. `ai-core`: переносимое ядро без личных данных

```text
ai-core/
├── AGENTS.md                   # короткий общий вход, собирается из исходников
├── VERSION                     # версия пакета правил и схем
├── rules/
│   ├── communication.md        # язык и подача
│   ├── workflow.md             # начало, выполнение, проверка, передача
│   ├── security.md             # переносимые границы безопасности
│   └── review.md               # общие критерии ревью
├── templates/
│   └── project/
│       ├── AGENTS.md
│       ├── CONTEXT.md
│       └── docs/
│           ├── STATE.md
│           ├── DECISIONS.md
│           └── HANDOFF.md
├── adapters/
│   ├── kimi/
│   ├── codex/
│   ├── claude/
│   ├── gemini/
│   └── web/
├── schemas/
│   ├── repository-registry.schema.json
│   ├── backup-manifest.schema.json
│   └── daily-report.schema.json
├── scripts/
│   ├── build.py                # собирает адаптеры
│   ├── validate.py             # проверяет источники и сгенерированные файлы
│   ├── sync.py                 # проверяет и обновляет управляемые блоки
│   ├── backup.sh               # создаёт неизменяемый комплект
│   └── restore-check.sh        # проверяет восстановление
└── tests/                      # тесты сборки, синхронизации и резерва
```

`ai-core` можно открыть команде без доступа к личным правилам и приватным проектам. Он содержит только общие механизмы, шаблоны и безопасные примеры.

### 2.2. `ai-personal`: только твои правила и реестр

```text
ai-personal/
├── AGENTS.md                   # личный слой поверх ai-core
├── rules/
│   └── personal.md             # личные предпочтения без секретов
├── projects.yml                # реестр личных проектов
├── contexts/                   # только личные контексты без отдельного репозитория
└── local.example.yml           # пример локальных путей, сами пути не передаются команде
```

Полные чаты, браузерные сессии, credentials и содержимое `~/.kimi-code` сюда не копируются. Личный репозиторий не нужен сотруднику для работы со студией.

### 2.3. `studio-private`: закрытая часть студии

```text
studio-private/
├── AGENTS.md
├── projects.yml
├── strategy/
├── finance/
├── contracts/
└── contexts/
```

Состав папок обозначает границы, а не требование немедленно переносить туда документы. Финансы, договоры, закрытые клиентские данные и стратегия не попадают в `ai-core` или `studio-team`.

### 2.4. `studio-team`: общий командный контур

```text
studio-team/
├── AGENTS.md                   # обязательные правила команды
├── STUDIO.md                   # роли, процессы, критерии готовности
├── projects.yml                # только разрешённые командные проекты
├── templates/
│   ├── issue.md
│   ├── pull-request.md
│   └── project/
├── roles.md                    # матрица доступа без персональных секретов
└── .github/
    ├── CODEOWNERS
    └── workflows/
```

Код и документы каждого клиентского проекта остаются в собственном репозитории. `studio-team` хранит реестр и стандарты, а не объединяет всех клиентов в один монорепозиторий.

### 2.5. Почему не один большой репозиторий

- Доступ к Git-репозиторию обычно открывает весь репозиторий, а не отдельные папки. Значит, `personal/` рядом с `team/` не является надёжной границей.
- Общий инструментарий нельзя помещать только в личный репозиторий, иначе команде придётся выдать доступ к личному.
- Разные репозитории позволяют назначить отдельные токены, правила ревью, расписания резерва и ключи шифрования.
- Реестр проектов даёт единую навигацию без единого хранилища с избыточными правами.

## 3. Папка `1_LLM` получит три зоны, а не зеркало всего компьютера

Предлагаемая структура внутри уже выбранной папки:

```text
1_LLM/
├── README.txt                  # назначение, запреты, порядок восстановления
│
├── 00_system/                  # только несекретная служебная информация
│   ├── storage-map.md          # эта карта и правила владения файлами
│   └── schema-version.txt      # текущая версия формата хранилища
│
├── 10_dist/                    # проверенные пакеты для ручной загрузки в веб-чаты
│   ├── core/
│   │   └── <version>/
│   │       ├── START_HERE.md
│   │       ├── AGENTS.md
│   │       └── manifest.json
│   └── studio-team/
│       └── <version>/
│           ├── START_HERE.md
│           ├── AGENTS.md
│           ├── STUDIO.md
│           └── manifest.json
│
└── 20_secure/                  # отдельные шифрованные корни rclone crypt
    ├── personal/
    │   ├── backups/
    │   │   └── <UTC-run-id>/
    │   ├── dist/
    │   └── ops/
    │       ├── daily/
    │       └── restore/
    ├── studio-private/
    │   ├── backups/
    │   ├── dist/
    │   └── ops/
    ├── studio-team/
    │   ├── backups/
    │   ├── dist/
    │   └── ops/
    └── projects/
        └── <project-id>/
            ├── backups/
            └── ops/
```

### 3.1. Назначение зон

| Зона | Что содержит | Кто пишет | Можно ли редактировать вручную |
|---|---|---|---|
| `README.txt` | Краткая инструкция без ссылок на приватные проекты и секретов | Владелец через изменение шаблона | Только через согласованную правку |
| `00_system` | Версия схемы и карта хранилища | Процесс публикации системной версии | Не является местом для рабочих правил |
| `10_dist` | Только очищенные пакеты, которые разрешено загружать в сторонние веб-чаты | Сборщик после проверки | Нет, создаётся новая версия |
| `20_secure/<scope>/backups` | Git bundle, снимок файлов, контрольные суммы и manifest | Отдельный процесс резерва области | Нет, комплект неизменяем |
| `20_secure/<scope>/dist` | Личные или приватные пакеты, которые нельзя хранить открыто | Сборщик со своим ключом области | Нет |
| `20_secure/<scope>/ops` | Зашифрованные отчёты запусков и восстановления | Только соответствующий агент | Нет, добавляется новая запись |

### 3.2. Что намеренно отсутствует

- Нет папки `INBOX`, из которой агент автоматически исполняет найденные инструкции. Случайный документ не должен получать управление системой.
- Нет `current/` с перезаписываемыми правилами. Новая версия складывается рядом, а адаптеры получают её через Git.
- Нет синхронизации всей домашней папки, `.venv`, кэшей, медиамоделей, браузерных профилей и сессий.
- Нет общего открытого списка всех клиентских проектов. Реестр хранится в Git с нужными правами, а не в `00_system`.
- Нет автоматического удаления старых копий на старте. Политика хранения включается после успешных проверок восстановления.

### 3.3. Как выглядит один резервный комплект

До применения `crypt` локальный комплект имеет понятную структуру:

```text
2026-11-27T05-47-00Z__<run-id>/
├── source.bundle               # полная история и refs Git
├── source.tar.gz               # файлы зафиксированного commit
├── SHA256SUMS                  # контрольные суммы bundle, архива и manifest
└── manifest.json               # загружается последним как признак завершения
```

Дата показывает формат имени, а не существующую копию. После загрузки через `rclone crypt` имена и содержимое внутри соответствующего защищённого корня шифруются. Просмотр и восстановление выполняются через правильный crypt remote, а не через обычное скачивание зашифрованных объектов из браузера.

## 4. Общий `AGENTS.md` будет собранным входом, а не гигантским исходником

Требование «один общий файл» сохраняется на стороне нейросети: она получает короткий `AGENTS.md`. Но люди редактируют тематические исходники, из которых этот файл собирается. Так одно обновление не требует вручную править пять копий.

### 4.1. Контракты файлов

| Файл | Содержит | Не содержит | Когда обновляется |
|---|---|---|---|
| `AGENTS.md` | Стартовый протокол, границы, обязательные ссылки, версии | Длинную историю и все задачи | При изменении устойчивых правил |
| `CONTEXT.md` | Цель, архитектуру, команды, термины и ограничения проекта | Текущие ежедневные статусы | При структурном изменении |
| `docs/STATE.md` | Текущий этап, доказанное, активную ссылку, следующий шаг | Полную доску задач | После проверенного шага |
| `docs/DECISIONS.md` | Дату, решение, причину, последствия и отмену | Несогласованные идеи как решения | Только после решения человека |
| `docs/HANDOFF.md` | Последнюю передачу: commit, файлы, проверки, блокеры | Бесконечный журнал всех сессий | В конце содержательной сессии |
| `rules/review.md` | Приоритеты и границы ревью | Правила выпуска только текстом | При изменении критериев |
| `REVIEW.md` | Адаптер облачного Claude Code Review | Универсальную память всех ИИ | Только если сервис включён |
| `projects.yml` | ID, область, владельца, репозиторий и трекер | Сами задачи и секретные URL | При добавлении или архивировании проекта |

### 4.2. Порядок сборки

```text
ai-core/rules/*
        +
Личный или студийный слой
        +
Правила конкретного проекта
        |
        v
Проверка конфликтов, ссылок, секретов и размера
        |
        v
AGENTS.md + адаптеры инструментов
        |
        v
Версия и контрольная сумма в каждом собранном файле
```

Правила более закрытой области не понижаются до более открытой. Проектный файл может добавить ограничение, но не отменяет запрет владельца. Локальные дополнения человека хранятся вне управляемого блока.

```markdown
<!-- AI-OS:BEGIN version=<version> sha256=<hash> -->
Сгенерированный общий блок. Руками не редактировать.
<!-- AI-OS:END -->

Локальные дополнения этого компьютера или инструмента.
```

### 4.3. `REVIEW.md` остаётся специальным адаптером

`REVIEW.md` не становится центром системы. Общие правила ревью редактируются в `ai-core/rules/review.md`, проект добавляет свои риски в собственном источнике. Сборщик создаёт `REVIEW.md` только для проекта, где фактически включён облачный Claude Code Review. Для локальных ревью используются поддерживаемые инструкции конкретного инструмента.

Это соответствует [официальному описанию Claude Code Review](https://code.claude.com/docs/en/code-review) и выводу предыдущего исследования: сервис на GitHub и локальная команда ревью имеют разные правила загрузки.

## 5. Личное, командное и приватное разделяются одновременно путями, токенами и ключами

Одной структуры папок недостаточно. Для каждой области фиксируются пять границ.

| Область | Git | Drive | Учётные данные | Кто видит |
|---|---|---|---|---|
| `personal` | `ai-personal` | `20_secure/personal` | Личный процесс резерва | Только владелец |
| `studio-private` | `studio-private` | `20_secure/studio-private` | Отдельный владелец или сервис приватного резерва | Владелец и отдельно допущенные |
| `studio-team` | `studio-team` | `20_secure/studio-team` и очищенный `10_dist/studio-team` | Сервисный аккаунт команды | Команда по роли |
| Проект клиента | Отдельный репозиторий | `20_secure/projects/<id>` | Только проектный доступ | Назначенная команда проекта |
| `public` | Отдельная публикация | Только явно одобренный экспорт | Публичный процесс без приватных токенов | Все после одобрения |

### 5.1. Проектируемые rclone remote

```text
aios-drive
  Корневая папка: выбранная 1_LLM
  Назначение: базовый Drive remote, без шифрования сам по себе

aios-personal-crypt
  remote = aios-drive:20_secure/personal

aios-private-crypt
  remote = aios-drive:20_secure/studio-private

aios-team-crypt
  remote = aios-drive:20_secure/studio-team

aios-project-<id>-crypt
  remote = aios-drive:20_secure/projects/<id>
```

Каждый автоматический процесс получает только конфигурацию своей области. Например, агент задач студии вообще не получает `aios-personal-crypt` и `aios-private-crypt`.

### 5.2. Важное ограничение `root_folder_id`

`root_folder_id` ограничивает корень, с которым работает rclone, но сам по себе не заменяет разграничение прав Google. Если выданный OAuth-токен имеет доступ ко всему Drive, ошибочная или скомпрометированная конфигурация может получить больше данных, чем задумано.

Поэтому защита строится так:

1. Отдельный Google-аккаунт или service account для автоматики.
2. Доступ только к необходимой папке области, насколько это поддерживает выбранная схема Drive.
3. Минимально достаточный OAuth scope, выбранный после реального теста доступа к уже существующей общей папке.
4. Разные crypt remote и разные пароли для личного, приватного и командного.
5. Пароль конфигурации rclone и офлайн-копия параметров восстановления.
6. Никаких OAuth JSON, токенов, паролей и salt в Git, отчётах или самой резервной папке.

Текущая папка находится в разделе «Доступные мне». Это подтверждает браузерный доступ выбранного аккаунта, но не подтверждает доступ service account или OAuth-приложения. Этот сценарий нужно отдельно проверить через rclone до любого расписания.

Основания: [rclone Google Drive](https://rclone.org/drive/) описывает OAuth, scope, `root_folder_id` и service accounts; [rclone crypt](https://rclone.org/crypt/) предупреждает, что пароль в обычной конфигурации лишь слабо скрыт, а потеря пароля и salt может сделать данные невосстановимыми.

## 6. Синхронизация правил между компьютерами идёт только через Git

### 6.1. До начала работы

```text
Открыть назначенный репозиторий
  -> проверить отсутствие чужих незакоммиченных правок
  -> git pull --ff-only
  -> прочитать AGENTS.md и обязательные документы
  -> выполнить sync --check
  -> сверить версию ядра, проекта и адаптера
  -> открыть задачу в трекере
```

Если рабочее дерево содержит чужие изменения, агент не очищает его и не прячет их. Если `pull --ff-only` невозможен, автоматическое обновление останавливается. Сначала разбирается состояние, затем начинается работа.

### 6.2. После проверенной работы

```text
Проверить исходный сценарий
  -> записать реальный результат проверки
  -> обновить STATE.md и HANDOFF.md
  -> добавить решение, только если его принял человек
  -> зафиксировать точные файлы в ветке, если коммит разрешён
  -> открыть PR
  -> пройти CI и назначенное ревью
  -> после merge другие компьютеры получают новую версию
```

### 6.3. Обновление адаптеров

1. На каждом устройстве `sync --check` сравнивает управляемый блок с выбранной версией.
2. При расхождении сначала показывается diff, без записи.
3. Перед первой записью создаётся локальная резервная копия изменяемого файла.
4. Запись затрагивает только управляемый блок.
5. После записи повторяются сборка и `sync --check`.
6. Новая сессия каждого инструмента должна назвать версию и источник, откуда её получила.
7. Ответ модели сверяется с файлом, потому что уверенный ответ сам по себе не доказывает загрузку.

### 6.4. Почему Drive не участвует в этом контуре

Drive не знает специальных путей Kimi, Codex, Claude и Gemini. Одновременная запись из двух мест не заменяет Git-ревью, а восстановление старого файла из облака может незаметно откатить правила. Поэтому Drive принимает выпущенные версии и резерв, но не раздаёт команды агентам автоматически.

## 7. Передача знаний между нейросетями имеет фиксированный протокол

### 7.1. Что передаётся

- Цель и границы задачи.
- Текущий этап и последний проверенный commit.
- Принятые решения с датами.
- Изменённые файлы и внешние эффекты.
- Полные результаты значимых проверок, включая неуспешные.
- Следующее физическое действие и блокер.
- Что не проверено и какие данные недоступны.

### 7.2. Что не передаётся

- Полный чат со всеми отвергнутыми гипотезами.
- Секреты, cookies, токены и содержимое приватных конфигураций.
- Непроверенные выводы под видом фактов.
- Личный контекст в командный или клиентский отчёт.
- Большой автоматический конспект без ссылки на источник.

### 7.3. Конец сессии

```text
Работа и проверки
  -> STATE.md: где находится проект
  -> DECISIONS.md: какие решения действительно приняты
  -> HANDOFF.md: что нужно следующему исполнителю
  -> Git: проверенный результат в ветке или PR
  -> Drive: только очередной резерв, не оперативная передача
```

`HANDOFF.md` перезаписывается как актуальная передача, а предыстория остаётся в Git. Так следующий чат получает одну страницу вместо архива предыдущих передач.

### 7.4. Начало новой сессии

Новая модель до изменений должна вернуть:

1. Цель и область данных.
2. Текущий этап и commit.
3. Действующие ограничения.
4. Что проверено и каким доказательством.
5. Следующий шаг, блокеры и неизвестное.

После этого выполняются пять одинаковых контрольных вопросов на каждом выбранном инструменте. Если ответы различаются, исправляется источник или адаптер, а не добавляется новый повторяющийся промпт.

## 8. Резервное копирование будет односторонним и неизменяемым

### 8.1. Последовательность одного запуска

```text
Получить блокировку области
  -> проверить репозиторий и чистоту commit
  -> выполнить validate.py и build.py --check
  -> создать git bundle и проверить его
  -> создать git archive конкретного commit
  -> записать manifest.json без локальных секретов
  -> рассчитать SHA-256
  -> загрузить файлы через crypt remote
  -> загрузить manifest последним
  -> скачать комплект во временную папку
  -> сверить SHA-256 и завершить запуск
```

Наличие manifest означает, что процесс дошёл до завершающей записи, но не заменяет последующий restore-тест. Неполный комплект без manifest считается неудачным и не выбирается для восстановления.

### 8.2. Пример manifest без чувствительных данных

```json
{
  "schema_version": 1,
  "run_id": "<UTC-time>_<random-id>",
  "repository_alias": "ai-personal",
  "scope": "personal",
  "commit": "<full-git-hash>",
  "created_utc": "<ISO-8601>",
  "source_state": "clean",
  "core_version": "<version>",
  "files": [
    "source.bundle",
    "source.tar.gz",
    "SHA256SUMS"
  ],
  "restore_test": "not_run_in_this_job"
}
```

В manifest не записываются имя пользователя ОС, абсолютные домашние пути, OAuth-данные, список приватных файлов с чувствительными названиями и содержимое задач.

### 8.3. Почему `copy`, а не `sync`

[Документация `rclone copy`](https://rclone.org/commands/rclone_copy/) прямо указывает, что команда не удаляет файлы в назначении. Для ежедневного резерва это безопаснее зеркала: исчезновение исходного файла не должно автоматически стирать последнюю копию.

Проектируемый режим:

```text
rclone copy <новый-комплект> <crypt-remote>:backups/<run-id> --immutable
```

Это схема будущей команды, а не выполненная настройка. Флаги и поведение будут проверены на тестовом комплекте. `sync` допускается только для отдельно согласованного второго зеркала уже зашифрованных данных, не для основного ежедневного процесса.

### 8.4. Незакоммиченная работа

Стандартный резерв фиксирует конкретный чистый commit. Если в репозитории есть незакоммиченные изменения:

- не создавать комплект с ложной пометкой чистого состояния;
- сохранить предыдущие копии;
- сообщить, что незакоммиченная работа не защищена;
- продолжить обработку других независимых репозиториев;
- завершить общий запуск с предупреждением или ошибкой по политике;
- предложить человеку WIP-ветку или отдельный ручной архив после проверки на секреты.

Автоматически собирать все untracked-файлы опасно: среди них могут оказаться ключи, локальные базы и чужие черновики.

### 8.5. Хранение копий

Стартовая политика после успешного пилота:

| Тип | Сколько держать | Когда включается |
|---|---|---|
| Ежедневные | 30 | После первых успешных restore-тестов |
| Еженедельные | 12 | После отдельной проверки выбора недельной копии |
| Ежемесячные | 12 | После согласования места и стоимости хранения |

Это рекомендуемые параметры, не ограничение Google. До включения очистки все новые комплекты сохраняются. Удаление старых копий требует отдельной проверки, журнала и запрета на удаление последней проверенной копии.

## 9. Восстановление доказывается до включения ежедневного расписания

### 9.1. Полный restore-тест

```text
Выбрать комплект с manifest
  -> скачать через правильный crypt remote в пустую папку
  -> проверить SHA256SUMS
  -> выполнить git bundle verify source.bundle
  -> клонировать bundle в новый репозиторий
  -> сверить HEAD с commit из manifest
  -> распаковать source.tar.gz отдельно и сверить содержимое
  -> запустить validate.py и build.py --check
  -> восстановить адаптеры в изолированный тестовый HOME
  -> прочитать ключевые AGENTS.md, STATE.md и HANDOFF.md
  -> записать датированный результат
```

Восстановление выполняется в пустой каталог, не поверх текущих правил. Секреты для рабочего восстановления вводятся отдельно и не становятся частью архива.

### 9.2. Критерий готовности резерва

Резерв считается работающим только когда одновременно верно:

- комплект скачан заново из Drive;
- контрольные суммы сошлись;
- bundle прошёл проверку и клонирование;
- commit совпал с manifest;
- валидация восстановленного источника прошла;
- ключевые документы читаются;
- процесс повторим на другом устройстве или с изолированным тестовым профилем;
- владелец знает, где лежат офлайн-параметры восстановления.

Сообщение `rclone copy` о загрузке не равно успешному восстановлению.

### 9.3. Контроль целостности crypt

Документация [rclone crypt](https://rclone.org/crypt/) указывает, что обычные хеши backend не сохраняются для crypt и предлагает `rclone cryptcheck` для проверки зашифрованного remote. В системе используются оба уровня: техническая проверка crypt и независимая проверка SHA-256 после расшифровки.

## 10. Ежедневный системный агент состоит из проверяемых шагов

Это не один большой prompt. Основу выполняет скрипт, а языковая модель только объясняет результат.

### 10.1. Предлагаемый ежедневный цикл

```text
06:47 НСК, проектное время
  |
  v
Проверить, не идёт ли другой запуск этой области
  |
  v
Для каждого разрешённого репозитория:
  - проверить доступ и чистоту
  - обновить только fast-forward, если это разрешено
  - проверить схемы, ссылки, секреты и размер
  - проверить актуальность адаптеров
  - создать новый неизменяемый резерв
  |
  v
Зафиксировать heartbeat и результат каждого шага
  |
  v
Получить свежие задачи через read-only API
  |
  v
Сформировать техническую сводку
  |
  +-> LLM недоступна: отправить техническую сводку без неё
  |
  +-> LLM доступна: объяснить приоритеты, ничего не меняя
```

Время 06:47 НСК остаётся предложением из общей архитектуры. Расписание пока не создано.

### 10.2. Таблица ответственности

| Действие | Скрипт | LLM | Человек |
|---|---|---|---|
| Проверка Git, ссылок, схем и версий | Выполняет | Не нужна | Разбирает ошибку |
| Создание bundle, архива и SHA-256 | Выполняет | Не нужна | Контролирует результат |
| Загрузка в Drive | Выполняет | Не нужна | Выдаёт доступ |
| Restore-тест | Выполняет по расписанию | Может объяснить ошибку | Периодически принимает результат |
| Сводка задач | Получает данные | Суммирует с источниками | Принимает решения |
| Изменение правил | Только проверяет | Может предложить | Утверждает через PR |
| Закрытие задачи | Не выполняет | Не выполняет | Подтверждает |
| Публикация и production | Не выполняет | Не выполняет | Даёт отдельное разрешение |

### 10.3. Журнал запуска

```yaml
schema_version: 1
run_id: <id>
scope: studio-team
started_at: <ISO-8601>
finished_at: <ISO-8601>
scheduler: <launchd|github-actions|vps>
validation: <passed|failed>
adapters: <current|stale|failed>
backup: <verified|failed|skipped>
restore_test: <passed|failed|not_scheduled>
tasks_api: <ok|unavailable|not_configured>
llm_summary: <ok|unavailable|disabled>
notification: <sent|failed>
```

Если один репозиторий не прошёл, отчёт содержит отдельный результат по нему. Ошибка не маскируется общим «успешно».

### 10.4. Наблюдение за отсутствием запуска

Heartbeat записывается после фактического результата. Если успешного резерва области нет более 25 часов, создаётся предупреждение. Порог 25 часов - стартовая проектная настройка для ежедневного процесса, а не внешний стандарт.

Отдельно контролируются:

- планировщик не запустился;
- запуск начался и завис;
- сеть или Drive недоступны;
- загрузка завершилась, но проверка не прошла;
- restore-тест давно не выполнялся;
- отчёт не доставлен.

## 11. Агент задач студии отделён от системного резерва

### 11.1. Два процесса с разными правами

| Свойство | Системный агент | Агент задач студии |
|---|---|---|
| Основная цель | Целостность знаний и резерв | Актуальность работы студии |
| Источники | Git и Drive | Трекер, PR и CI |
| Доступ к личному | Только личный процесс владельца | Нет |
| Доступ к приватному студийному | Только отдельный приватный процесс | Нет по умолчанию |
| Запись | Новые резервы и журналы | Сначала только черновик отчёта |
| Закрытие задач | Нет | Нет |
| Изменение правил | Нет | Нет |

Не нужен один всезнающий агент со всеми токенами. Общий календарь может запускать оба процесса, но их конфигурации и журналы остаются разными.

### 11.2. Источник и поля задачи

Если существующего трекера нет, стартовый вариант - GitHub Projects с Issues. При наличии работающего трекера он сохраняется, а GitHub не вводится как второй источник.

Минимальные поля:

```text
id и ссылка
scope: studio-team | studio-private
project
owner
status
priority
due, если срок реально существует
next_action
blocker и ответственный за разблокировку
acceptance
evidence
updated_at
```

### 11.3. Стартовые права

Разрешено на первом этапе:

- читать только командный Project;
- читать связанные PR и статусы CI;
- формировать ежедневную сводку;
- создавать черновик отчёта в зашифрованной области;
- помечать недоступные источники как «нет данных».

Не разрешено без отдельного этапа:

- менять чужие статусы;
- закрывать задачи;
- назначать людей;
- публиковать комментарии;
- читать личные проекты;
- получать production-секреты;
- менять правила, hooks и workflows.

### 11.4. Формат сводки

```text
Вывод: сколько задач требует решения владельца и что является главным блокером.

Требуют решения:
- задача, владелец, блокер, время последнего события, ссылка.

Просрочено:
- задача, срок, следующее действие, ссылка.

Ожидает ревью:
- PR, состояние проверок, чьё решение нужно.

Принято людьми за период:
- задача и доказательство результата.

Данные: источник и фактическое время API-запроса.
Нет данных: недоступные проекты и причина.
```

Ошибка API отображается как отсутствие данных, а не как ноль просроченных задач. Личные задачи не попадают в командную сводку.

## 12. Команда работает со своими подписками, а знания получает через общий Git

### 12.1. Подключение сотрудника

```text
Личный аккаунт сотрудника в GitHub
  -> доступ к studio-team и назначенному проекту
  -> клонирование на его компьютер
  -> установка только выбранного адаптера
  -> validate.py и sync --check
  -> новая сессия называет версию и критерий готовности
  -> одна тестовая задача через ветку и PR
  -> только затем расширение доступа
```

Не передаются аккаунт владельца Kimi, Claude, ChatGPT или Gemini, его браузерные cookies и личные OAuth-токены. Подписка сотрудника определяет его инструмент, но не круг доступа к знаниям.

### 12.2. Единый рабочий цикл

```text
Задача в трекере
  -> ветка
  -> работа на любой разрешённой нейросети
  -> реальные проверки
  -> STATE.md и HANDOFF.md
  -> pull request
  -> CI и ревью
  -> одобрение назначенного человека
  -> merge
  -> приёмка и статус задачи
```

### 12.3. Серверные замки

Для `main` проектируются обязательный PR, нужные проверки, запрет force push, ревью владельца правил и сброс устаревших одобрений после нового commit. `CODEOWNERS` назначает ответственных за `AGENTS.md`, `REVIEW.md`, workflows, hooks и скрипты резерва.

Локальный текстовый запрет остаётся подсказкой. Реальную границу дают permissions, hooks, защита ветки и ограниченные права внешних сервисов. Основания: [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners), [статья о восьми запретах](https://raytsystem.ru/m/zamki-dlya-claude-code-8-zapretov-kotorye-agent-ne-oboydet).

## 13. Конфликты и ошибки обрабатываются без «победил последний файл»

| Ситуация | Автоматическое поведение | Что требуется от человека |
|---|---|---|
| Два компьютера изменили один источник | Остановить fast-forward или merge при конфликте | Разрешить через PR и проверку |
| Изменился только `HANDOFF.md` | Показать обе версии и доказательства | Оставить актуальную передачу без потери истории Git |
| В Drive появился более новый файл | Не применять его как правило | Выпустить новую версию через Git |
| Незакоммиченные чужие файлы | Не удалять, не прятать, не включать молча в архив | Разобрать владельца и назначение |
| Повторный ежедневный запуск | Не запускаться параллельно с активным | Разобрать зависший lock по журналу |
| Обрыв сети во время загрузки | Комплект без manifest считается неполным | Повторить новым run-id или штатным retry |
| Drive возвращает ошибку | Сохранить локальный комплект и записать сбой | Проверить доступ, квоту и авторизацию |
| LLM недоступна | Резерв и валидация продолжаются | Нет действия, если техническая сводка доставлена |
| API трекера недоступен | «Нет данных», не ноль задач | Проверить токен и источник |
| Контрольная сумма не сошлась | Не восстанавливать комплект | Выбрать предыдущую проверенную копию |
| Потерян crypt password или salt | Не подбирать и не менять старую конфигурацию | Использовать офлайн-восстановление |
| Сотрудник ушёл | Ничего не удалять автоматически | Отозвать Git, Drive, трекер и переназначить задачи |

Ни один конфликт правил не разрешается силами LLM без человека. Модель может объяснить diff, но не выбирает норму самостоятельно.

## 14. Внедрение разбито на восемь проверяемых этапов

### Этап 0. Согласование карты

**Действия:** подтвердить четыре репозитория, три зоны Drive, области данных, владельцев и источник задач.

**Результат:** зафиксированное решение и список первого пилота.

**Проверка:** структура понятна владельцу, все неизвестные доступы явно перечислены.

**Сейчас:** выполняется именно этот этап. Drive не изменён.

### Этап 1. Локальный каркас и личный пилот

**Действия:** создать `ai-core` и `ai-personal`, добавить шаблоны и реестр, выбрать один проект. Рекомендуемый пилот - документы текущего переезда `Kimi.ai`, без переноса `.venv`, моделей, MP3 и кэшей.

**Результат:** новый чат находит цель, состояние, решения и следующий шаг без старой переписки.

**Проверка:** снимок существующих правил сохранён, файлы не удалены, секретов нет, пять контрольных вопросов отвечают на источники.

### Этап 2. Сборщик и адаптеры

**Действия:** реализовать `build.py`, `validate.py`, `sync.py --check` и адаптеры только для фактически используемых инструментов.

**Результат:** одно изменение источника даёт предсказуемый diff во всех выбранных адаптерах.

**Проверка:** тесты на устаревшую версию, локальные дополнения, двойной импорт, запрещённую ссылку и попытку записи вне управляемого блока. Затем одна реальная задача в каждом выбранном инструменте.

### Этап 3. Структура Drive и ручной резерв

Этап имеет две части, чтобы тест доступа не зависел от ещё ненаписанного сборщика.

**3A. Доступ и безопасный тест, можно начать сразу после этапа 0:** создать согласованные папки, настроить `aios-drive` и один crypt remote, загрузить и скачать несекретный тестовый файл с заранее известной контрольной суммой. Реальные правила и личные данные для этого не нужны.

**Результат 3A:** подтверждены запись, чтение, шифрование и повторное скачивание именно в выбранной общей папке.

**3B. Полный резерв после этапов 1 и 2:** создать резерв пилота со связанными `validate.py` и `build.py --check`, затем восстановить его в пустой каталог.

**Результат 3B:** полный комплект из Drive восстановлен, валидатор и сборщик работают на восстановленной копии.

**Проверка:** браузерная структура, доступ именно к общей папке, `rclone copy`, SHA-256, `git bundle verify`, клонирование, `validate.py`, отсутствие секретов в логах.

**Стоп-условие:** если OAuth или права общей папки не работают, 3B и расписание не начинаются. Сначала чинится доступ, без переноса резерва в другое место молча.

### Этап 4. Ежедневная техническая автоматика

**Действия:** добавить блокировку, heartbeat, журнал, уведомления и расписание. Для личного MVP предлагается `launchd` на Mac; для командного постоянного контура отдельно выбираются GitHub Actions или VPS.

**Результат:** ежедневная проверка и резерв идут без открытого чата и без LLM.

**Проверка:** ручной запуск, запуск по расписанию, повторный запуск, выключенная сеть, недоступный Drive, dirty repo, параллельный запуск и предупреждение об отсутствии резерва.

### Этап 5. Командный контур

**Действия:** создать `studio-team`, подключить тестового сотрудника с его собственной подпиской, включить PR, CI, CODEOWNERS и защищённую ветку.

**Результат:** сотрудник видит командное и назначенный проект, но не личное и приватное.

**Проверка:** матрица доступов на тестовой учётной записи, PR на правила останавливается без владельца, force push запрещён сервером.

### Этап 6. Агент задач студии

**Действия:** подключить выбранный трекер read-only, реализовать сводку, затем отдельно согласовать комментарии и события.

**Результат:** сводка показывает реальные задачи, владельцев, блокеры и доказательства.

**Проверка:** ошибка API, личная задача, просрочка, зависание, PR без доказательств, попытка закрыть задачу и попытка прочитать личный репозиторий.

### Этап 7. Масштабирование и хранение

**Действия:** подключать проекты по одному, проводить ежемесячный restore-тест, только затем включать очистку старых копий.

**Результат:** система обслуживает несколько проектов без потери границ и контроля восстановления.

**Проверка:** полный аудит областей, повторное восстановление выбранных проектов, отсутствие последней копии в списке на удаление, согласованная стоимость хранения.

## 15. Приёмка всей системы проверяется сценариями, а не числом созданных папок

### 15.1. Общие правила

- Один исходник выпускает одну версию для всех выбранных инструментов.
- Kimi, Codex, Claude и Gemini на своих реальных сессиях называют одинаковую версию и источник.
- Локальные дополнения не исчезают после обновления.
- Двойного импорта и противоречащих управляемых блоков нет.
- `REVIEW.md` создаётся только там, где нужен соответствующий сервис.

### 15.2. Передача контекста

- Новый чат без старой истории правильно отвечает на пять контрольных вопросов.
- Ответ содержит ссылки на конкретные файлы и commit.
- Непроверенное названо непроверенным.
- Следующий шаг совпадает с задачей трекера.
- Старая передача не переопределяет более свежий проверенный `STATE.md`.

### 15.3. Резерв

- Каждый запуск создаёт новый комплект и не удаляет предыдущие.
- Неполная загрузка не считается пригодной к восстановлению.
- Повреждение обнаруживается контрольной суммой.
- Восстановление в пустой каталог проходит полностью.
- Без crypt password и salt данные не читаются.
- Параметры восстановления существуют офлайн и не хранятся только на том же Mac.

### 15.4. Команда и безопасность

- Подрядчик не видит другие проекты и личные данные.
- Агент задач не имеет токенов резерва личного и приватного контуров.
- PR на правила, hooks, workflows и backup требует назначенного владельца.
- Сервер запрещает merge без проверок и force push.
- Чтение секретов проверяется через все доступные инструменты, не только через Bash.
- После отзыва доступа закрываются Git, Drive и трекер, а рабочие материалы остаются организации.

### 15.5. Ежедневная работа

- Отсутствие запуска обнаруживается, а не только явная ошибка.
- Недоступность LLM не отменяет резерв.
- Недоступность трекера не превращается в «ноль проблем».
- Личное не попадает в командный отчёт.
- Агент не закрывает задачу и не публикует результат за человека.

## 16. Эксплуатация имеет небольшой набор регулярных действий

| Период | Действие | Доказательство |
|---|---|---|
| Ежедневно | Валидация, резерв, heartbeat, сводка задач | Журнал запуска и свежий комплект |
| Еженедельно | Разбор ошибок, устаревших адаптеров и зависших задач | Список исправлений с источниками |
| Ежемесячно | Реальное восстановление выбранной области | Restore-отчёт и проверенный commit |
| При добавлении проекта | Классификация, владелец, трекер, резерв | Запись в реестре и тест доступа |
| При смене правил | PR, сборка, проверка моделей | Версия, diff и результаты сессий |
| При уходе сотрудника | Отзыв доступов и переназначение | Чек-лист offboarding |
| При смене OAuth или crypt | Новый тест записи и восстановления | Новый успешный restore без потери старого доступа |

Метрики полезности: доля активных проектов со свежим состоянием, дата последнего успешного restore, число противоречий адаптеров, активные задачи без владельца или следующего действия, повторные ошибки и утечки между областями. Количество файлов и hooks само по себе успехом не является.

## 17. Предлагаемые решения по умолчанию для следующего шага

Чтобы не блокировать внедрение непринципиальными вопросами, предлагаю такие стартовые настройки:

| Вопрос | Предлагаемый выбор | Причина |
|---|---|---|
| Пилот | Документы проекта `Kimi.ai`, без тяжёлых медиа и окружений | Уже есть реальное состояние и передачи между чатами |
| Трекер | Сохранить существующий; если его нет, GitHub Projects | Не создавать вторую доску |
| Личный scheduler | `launchd` на Mac для MVP | Не требует нового сервера на пилоте |
| Командный scheduler | GitHub Actions или VPS после этапа 5 | Нужен независимый контроль и сервисные права |
| Время | 06:47 НСК | До начала рабочего дня, уже предложено в общей архитектуре |
| Резерв | `git bundle` + `git archive` + manifest + SHA-256 + crypt | Восстановление и истории, и рабочего снимка |
| Удаление старых копий | Выключено на пилоте | Сначала доказать восстановление |
| LLM в ежедневном процессе | Отключена на первом этапе | Технический результат не должен зависеть от модели |
| Права агента задач | Read-only | Сначала проверить качество данных и границы |

Платные API для этой архитектуры не нужны. Возможные расходы на GitHub, Google-хранилище, VPS и необязательные LLM-запросы не оцениваются до выбора конкретного тарифа и измерения объёма. Покупки и платные вызовы не входят в следующий шаг.
