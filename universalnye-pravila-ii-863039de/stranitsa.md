# Единая система правил и знаний для всех нейросетей

**Вывод: вам нужен не один большой файл, а управляемая система с одним универсальным входом `AGENTS.md`.** Правила, текущее состояние, решения и задачи должны храниться отдельно. Приватный Git становится источником истины, Google Диск принимает шифрованные резервные копии, а ежедневный агент проверяет целостность и готовит сводку, но не изменяет правила по собственному решению.

> **Рекомендуемая конфигурация**
>
> - `AGENTS.md` - короткий файл, который объясняет любой нейросети, кто вы, как работать и где лежит актуальный контекст.
> - `STATE.md`, `DECISIONS.md` и `HANDOFF.md` - состояние проекта, причины решений и передача работы следующему чату.
> - Отдельные пространства для личного, приватного студийного и командного. Разделение обеспечивается репозиториями и правами, а не только папками.
> - GitHub Projects или ваш текущий трекер - единственный источник статусов задач. Второй список задач в Markdown не нужен.
> - Ежедневный робот выполняет проверки и резервное копирование. Языковая модель только суммирует и предлагает.

Дата исследования: 25.11.2026. Ниже - архитектура, готовые шаблоны, порядок внедрения и проверки. Это проект решения, а не утверждение, что автоматика уже установлена на ваших компьютерах.

## 1. Система решает четыре разные задачи, которые нельзя смешивать

Обычно запрос «сделай общий файл для всех нейросетей» объединяет четыре вещи:

| Задача | Что храним | Как нейросеть получает |
|---|---|---|
| Постоянное поведение | Язык, формат ответов, границы, этапы работы | Автоматически загружаемый `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` |
| Знание проекта | Цель, архитектура, команды, решения, текущий этап | Проектный `AGENTS.md` и документы по его ссылкам |
| Актуальная работа | Задача, владелец, статус, блокер, следующий шаг | Трекер задач и свежий `STATE.md` |
| Безопасность | Запреты на секреты, удаление, выпуск, доступы | Permissions, hooks, CI, защищённые ветки и права |

Главная ошибка - записать всё это в один файл. Он быстро станет огромным, устареет и будет передавать команде лишнее. У каждого вида информации своя скорость изменения и своя аудитория.

Правильная схема выглядит так:

```text
Личные правила        Правила студии        Правила проекта
       \                    |                    /
        \___________________|___________________/
                            |
                     Сборщик инструкций
                            |
          +-----------------+------------------+
          |                 |                  |
       AGENTS.md        CLAUDE.md          GEMINI.md
       Codex/Kimi       Claude Code        Gemini CLI
          |                 |                  |
          +-----------------+------------------+
                            |
               Проверка версии и поведения
                            |
                Git + шифрованный архив
                            |
                       Google Drive
```

`AGENTS.md` - это оглавление и договор работы, а не вся база знаний. Он должен быть достаточно маленьким, чтобы нейросеть стабильно удерживала его в контексте.

## 2. Из статьи стоит взять метод проверки, но не абсолютные обещания

В [статье «Хуки для Claude Code: 8 запретов»](https://raytsystem.ru/m/zamki-dlya-claude-code-8-zapretov-kotorye-agent-ne-oboydet) правильно разделены текстовая просьба и технический запрет. Официальная документация Claude подтверждает: `CLAUDE.md` является контекстом, а не принудительной конфигурацией. Для блокировки действий нужны permissions или `PreToolUse` hooks ([Claude Code, память](https://code.claude.com/docs/en/memory), [Claude Code, hooks](https://code.claude.com/docs/en/hooks)).

Полезные идеи статьи:

- В задаче заранее пишут «Готово, когда» и ожидаемый результат проверки.
- Агент показывает вывод тестов, сборки или реального запроса, а не просто пишет «готово».
- Ревью сосредотачивается на рисках конкретного проекта.
- У защиты есть тесты на запрещённое и на разрешённое действие.
- После повторных неудач агент останавливается и пересматривает подход.
- Риск выпуска определяется затронутой областью: деньги, доступы и данные требуют человека.

Но три утверждения требуют поправки.

### 2.1. `REVIEW.md` не универсален

По [официальной документации Claude Code Review](https://code.claude.com/docs/en/code-review):

- облачный Code Review для GitHub использует `REVIEW.md` из базовой или основной ветки;
- этот сервис доступен организациям на Team и Enterprise;
- локальная команда `/code-review` доступна на любом тарифе;
- облачный сервис не выполняет код и сам по себе не блокирует pull request.

Следовательно, `REVIEW.md` - специализированный адаптер одного сервиса. Он не заменяет общие правила и не читается всеми нейросетями.

Чтобы не разъезжались копии, правила ревью хранятся в одном `rules/review.md`, а сборщик создаёт:

- раздел `## Code Review Rules` в проектном `AGENTS.md` для Codex и других читающих его инструментов;
- раздел «Ревью» в `CLAUDE.md` для локального Claude;
- `REVIEW.md` только при включённом облачном Claude Code Review.

При этом облачный Claude использует `REVIEW.md` из базовой ветки, поэтому изменение правил ревью начинает действовать после принятия в основную ветку, а не прямо из чужого PR.

### 2.2. Hook на `Bash` не закрывает все пути

Пример из статьи проверяет команды `cat`, `grep`, `cp` и другие shell-команды. Но агент может прочитать файл инструментом `Read`, изменить защиту через `Write`, использовать другой инструмент или MCP. Значит, формулировка «агент не обойдёт» слишком сильная.

Для секретов нужны одновременно:

- запреты чтения и записи на уровне разрешений инструмента;
- hooks для всех релевантных инструментов, а не только `Bash`;
- отсутствие секретов в рабочей папке, если они там не нужны;
- серверные ограничения для выпуска и изменения защит;
- тест обхода каждым доступным агенту способом.

### 2.3. Восемь запретов - пример политики, а не универсальный стандарт

Полный запрет `git rebase`, `git stash` или `git add -A` может быть полезен в одном проекте и мешать в другом. Их нельзя механически копировать во все нейросети и репозитории. Сначала определяют риск, затем пишут правило и тест.

Для команды главный замок находится не на ноутбуке, а на сервере. [Защищённые ветки GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) умеют требовать pull request, ревью, успешные проверки, запрещать force push и сбрасывать устаревшие одобрения после нового коммита. Это надёжнее локального файла-доказательства.

## 3. Единый файл должен быть входом в систему, а не базой всего знания

[AGENTS.md](https://agents.md/) - открытый Markdown-формат для инструкций кодирующим агентам. Он поддерживается экосистемой инструментов, не требует обязательных полей и допускает вложенные файлы. Более близкий к редактируемому файлу `AGENTS.md` имеет приоритет над общим.

Но даже здесь нет единого стандарта импортов, лимитов и глобальных путей для всех продуктов. Поэтому нужна небольшая система адаптеров.

### Рекомендуемая структура знаний

| Файл | Назначение | Кто меняет | Как часто |
|---|---|---|---|
| `AGENTS.md` | Устойчивые правила и порядок запуска | Владелец или команда через ревью | Редко |
| `CONTEXT.md` | Цель, границы, архитектура, термины | Команда проекта | При изменении устройства |
| `STATE.md` | Текущий этап, что сделано, что дальше | Исполнитель после проверенного шага | После работы |
| `DECISIONS.md` | Решения, причины, дата, что отменено | Тот, кто принял решение | По событию |
| `HANDOFF.md` | Короткая передача следующему чату | Агент или человек в конце сессии | Каждая сессия |
| `REVIEW.md` | Правила облачного Claude Code Review | Через защищённое ревью | Редко |
| Задачи в трекере | Статус, владелец, срок, блокер | Люди и автоматика с аудитом | Постоянно |

Не помещайте в `AGENTS.md` список всех текущих задач, длинные журналы, полные переписки, пароли, клиентские секреты и всю историю проекта. Это делает контекст хуже и повышает риск утечки.

### Минимальный бюджет контекста

Это рабочие ограничения проекта, а не законы нейросетей:

- личный глобальный `AGENTS.md` - ориентир 100-180 строк;
- проектный `AGENTS.md` - ориентир до 150 строк;
- `STATE.md` - одна-две страницы;
- `HANDOFF.md` - до одной страницы;
- длинные инструкции выносятся в отдельные процедуры и загружаются по необходимости.

Claude прямо рекомендует держать `CLAUDE.md` компактным и ориентируется примерно на 200 строк. Codex по умолчанию ограничивает суммарные инструкции 32 КиБ. У других систем свои ограничения, поэтому короткий общий знаменатель практичнее.

## 4. Личное, студийное и командное разделяются правами доступа

Папки `personal/` и `team/` внутри одного репозитория не разделяют доступ: человек с клоном репозитория видит всё. Поэтому классификация должна совпадать с границами репозиториев.

### Четыре области информации

| Область | Что относится | Кто видит | Где хранить |
|---|---|---|---|
| `personal` | Личные планы, предпочтения, семейные и бытовые проекты | Только вы | `ai-personal`, приватно |
| `studio-private` | Стратегия, финансы, договоры, коммерческие условия, закрытые данные клиентов | Вы и отдельно допущенные люди | `studio-private`, приватно |
| `studio-team` | Процессы студии, шаблоны, общие стандарты, задачи и материалы для исполнителей | Команда по ролям | `studio-team`, организация GitHub |
| `public` | Проверенные публичные материалы | Все | Отдельная публикация после одобрения |

Простой тест классификации:

1. Это связано со студией, клиентом, доходом или рабочим результатом? Если нет, это `personal`.
2. Можно ли показать это любому действующему члену команды без вреда? Если нет, это `studio-private`.
3. Это необходимо команде для работы? Если да, это `studio-team`.
4. Можно ли опубликовать внешнему человеку? Только после отдельной проверки это `public`.

Если сомневаетесь, выбирайте более закрытую область. Агент не должен самостоятельно понижать конфиденциальность.

### Рекомендуемые репозитории

```text
ai-personal/                 только ваши личные правила и реестр личных проектов
studio-private/              закрытая стратегия и приватные проекты студии
studio-team/                 общие правила, шаблоны и реестр командных проектов
project-client-a/            обычный репозиторий проекта со своим AGENTS.md
project-client-b/            другой проект и другой круг доступа
```

Не обязательно создавать всё сразу. Начните с `ai-personal` и одного проекта, затем добавьте `studio-team`. `studio-private` создаётся до первой записи финансов, договоров или закрытых клиентских данных.

## 5. Структура единого источника истины

Ниже - достаточная структура без тяжёлой платформы.

```text
ai-personal/
├── AGENTS.md                    # исходник ваших глобальных правил
├── rules/
│   ├── communication.md         # язык, стиль, формат ответов
│   ├── workflow.md              # этапы и критерий готовности
│   ├── security.md              # переносимые запреты
│   └── review.md                # общие критерии ревью
├── projects.yml                 # реестр личных проектов
├── adapters/
│   ├── claude/
│   ├── codex/
│   ├── gemini/
│   └── kimi/
├── scripts/
│   ├── build.py                 # собирает файлы из источников
│   ├── validate.py              # схема, ссылки, конфликты, лимиты
│   ├── sync.py                  # обновляет управляемые блоки
│   └── backup.sh                # версия + архив + отправка
├── dist/                        # сгенерированные комплекты
└── reports/                     # ежедневные технические отчёты

studio-team/
├── AGENTS.md                    # обязательные правила командной работы
├── STUDIO.md                    # как устроена студия и её процессы
├── projects.yml                 # только командные проекты
├── templates/
├── .github/
│   ├── CODEOWNERS
│   └── workflows/
└── reports/                     # общая сводка без личных данных

project-client-a/
├── AGENTS.md                    # правила именно этого проекта
├── CONTEXT.md                   # устройство и границы проекта
├── docs/
│   ├── STATE.md
│   ├── DECISIONS.md
│   └── HANDOFF.md
├── REVIEW.md                    # только если используется Claude Code Review
├── .claude/                     # локальные адаптеры Claude
├── .github/                     # CI, CODEOWNERS, шаблоны
└── src/
```

Правило одного владельца данных:

- правила редактируются только в исходниках;
- `dist/` не редактируется руками;
- статус задачи существует только в трекере;
- `STATE.md` объясняет этап проекта, но не дублирует доску задач;
- отчёт агента не становится источником истины автоматически.

## 6. Готовый шаблон вашего глобального `AGENTS.md`

Это основа, которую можно адаптировать. Она намеренно не содержит конкретных проектов и секретов.

```markdown
# Мои правила работы с ИИ

Версия: 1.0.0
Владелец: Артём

## 1. Приоритет и границы

- Соблюдай безопасность, права доступа и условия текущей задачи.
- Не раскрывай секреты, токены, пароли, cookies и содержимое .env.
- Не публикуй, не отправляй внешние данные и не меняй прод без моего явного разрешения.
- Не удаляй данные, не переписывай историю Git и не отключай проверки.
- При конфликте правил остановись и покажи конфликт. Более закрытая область данных побеждает.
- Не выдумывай факты о проекте. Отделяй подтверждённое, предположение и неизвестное.

## 2. Определи область перед работой

- personal: личное, не связанное со студией.
- studio-private: студия, но не для общей команды.
- studio-team: командная работа студии.
- public: уже разрешено публиковать.

Не переноси информацию между областями без необходимости и разрешения.
Если область непонятна, считай её studio-private и спроси.

## 3. Начало каждой сессии

1. Прочитай ближайший AGENTS.md и его обязательные ссылки.
2. Если существуют, прочитай CONTEXT.md, docs/STATE.md, docs/DECISIONS.md и docs/HANDOFF.md.
3. Если указана задача, открой её в трекере. Не полагайся на старую копию статуса.
4. До изменений напиши коротко: цель, область, текущий этап, что проверено, что неизвестно.
5. Если контекст противоречив или отсутствует, сначала задай блокирующий вопрос.

## 4. Этапы работы

1. Результат: сформулируй, что должно измениться.
2. Границы: назови файлы, данные и действия, которые нельзя трогать.
3. Риск: FAST, STANDARD или RELEASE_CRITICAL.
4. Проверка: заранее определи команду, реальный сценарий и ожидаемый вывод.
5. Выполнение: делай минимальное достаточное изменение.
6. Доказательство: запусти проверку и покажи результат дословно.
7. Передача: обнови STATE.md и HANDOFF.md только подтверждёнными фактами.

## 5. Готово, когда

- Выполнен исходный пользовательский сценарий, а не только import или компиляция.
- Проверки, относящиеся к изменению, зелёные.
- Нет неучтённых изменений и временных файлов.
- Названо, что проверено и что осталось непроверенным.
- Для RELEASE_CRITICAL получено моё отдельное разрешение.

Не пиши «готово» без доказательства.

## 6. Ограничение попыток

- Не больше двух одинаковых попыток одной проверки.
- После второй остановись, объясни причину и предложи другой подход.
- Не исправляй unrelated ошибки и старый код без отдельной задачи.

## 7. Коммуникация

- Отвечай по-русски, коротко и по существу.
- Сначала вывод, затем 2-4 независимых довода, затем факты.
- Для действий называй конкретный файл, команду, результат и следующий шаг.
- Не скрывай неудачную проверку и не представляй план как выполненную работу.

## 8. Знания после работы

- В DECISIONS.md записывай только принятые решения с датой и причиной.
- В STATE.md записывай текущий этап, проверенное, следующий шаг и блокеры.
- В HANDOFF.md записывай commit, изменённые файлы, результаты проверок и следующий шаг.
- Не сохраняй секреты и полные личные переписки в общую память.

## 9. Ревью

- Сначала деньги, безопасность, данные, доступы и потеря работы.
- Проверяй текущий diff, старое отмечай отдельно.
- Указывай файл, строку, риск и способ воспроизведения.
- Не считай одобрение ИИ одобрением человека.
```

### Как этот файл заполняется

Не генерируйте окончательную версию одним промптом. Порядок такой:

1. Соберите существующие `CLAUDE.md`, `AGENTS.md`, правила Codex, заметки и повторяющиеся инструкции.
2. Разделите их на поведение, проект, состояние, задачи и технические запреты.
3. Удалите повторы и противоречия.
4. Переведите проверяемые действия в permissions, hooks и CI.
5. Оставьте в глобальном файле только то, что нужно почти в каждой сессии.
6. Проверьте на пяти реальных задачах в разных нейросетях.
7. Зафиксируйте версию и изменяйте дальше через короткие ревью.

## 7. Шаблоны проекта и передачи знаний

### 7.1. Проектный `AGENTS.md`

```markdown
# Проект: [название]

Область: personal | studio-private | studio-team
Владелец: [человек]
Трекер: [ссылка]

## Цель

[Одна проверяемая фраза]
```

## 8. Как один исходник становится общим для разных нейросетей

Общим файл делает не название, а процесс:

```text
Одобренный исходник в Git
        ↓
Сборка под конкретный инструмент
        ↓
Установка в известный инструменту путь
        ↓
Проверка, что нужная версия реально загружена
```

Не используйте Google Диск как механизм автоматической раздачи правил. Он не знает специальных путей нейросетей, плохо решает конфликты одновременного редактирования и может превратить резервную копию в источник непроверенных инструкций.

### Таблица адаптеров

| Инструмент | Глобальный уровень | Проектный уровень | Рекомендуемое подключение |
|---|---|---|---|
| Kimi Code | `~/.agents/AGENTS.md` для общих правил, `~/.kimi-code/AGENTS.md` для специфики Kimi | `AGENTS.md` | Общий исходник в generic-путь, отдельные Kimi-настройки не дублировать |
| Codex | `~/.codex/AGENTS.md` | `AGENTS.md`, при необходимости `AGENTS.override.md` | Сгенерированный глобальный файл и проектный `AGENTS.md` |
| Claude Code | `~/.claude/CLAUDE.md` | `CLAUDE.md` и ближайшие вложенные файлы | В `CLAUDE.md` указать `@AGENTS.md`; специфику Claude писать ниже |
| Gemini CLI | `~/.gemini/GEMINI.md` | `GEMINI.md` или настроенный `AGENTS.md` | Настроить `context.fileName` либо импортировать общий файл |
| Cursor и другие coding agents | Зависит от продукта | Обычно поддерживается `AGENTS.md` | Проектный файл как общий знаменатель, глобальные настройки проверять отдельно |
| GitHub Copilot coding agent | Зависит от среды | `AGENTS.md` и поддерживаемые GitHub-инструкции | Не дублировать без необходимости, проверить конкретную версию |
| ChatGPT, Claude, Gemini в обычном веб-чате | Project, Gem или настройки приложения | Файлы проекта и стартовый промпт | Загрузить собранный комплект, не ожидать автоматического чтения локального `AGENTS.md` |
| Собственный агент через API | System prompt и инструменты | Контекст, полученный из Git или API | Сборщик вставляет нужные документы явно |

Основания для путей: [Kimi Code, расположение данных](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/data-locations.html), [Codex, AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Claude Code, память](https://code.claude.com/docs/en/memory), [Gemini CLI, контекст](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md).

### 8.1. Kimi Code

Официальная документация Kimi различает:

- `$KIMI_CODE_HOME/AGENTS.md`, по умолчанию `~/.kimi-code/AGENTS.md` - глобальные инструкции именно Kimi;
- `~/.agents/AGENTS.md` - generic-инструкции, которые могут быть общими между инструментами;
- `~/.agents/skills/` - общие skills;
- сессии и credentials - отдельные локальные данные, не общая база знаний.

Практический вариант: переносимые правила держать в `~/.agents/AGENTS.md`, а в `~/.kimi-code/AGENTS.md` оставить только поведение, специфичное для Kimi. Не копируйте один длинный текст в оба файла без проверки, иначе получите дублирование контекста.

### 8.2. Codex

Codex читает глобальный `~/.codex/AGENTS.md`, затем проектные файлы от корня до текущей директории. `AGENTS.override.md` имеет приоритет на соответствующем уровне. По умолчанию действует суммарный лимит 32 КиБ. Новая сессия перестраивает цепочку инструкций.

Проверка:

```bash
codex --ask-for-approval never "Назови версию AI_OS_VERSION и перечисли активные источники инструкций. Ничего не меняй."
```

Ответ модели дополнительно сверяют с реальными файлами. Если версия старая, проверяют `CODEX_HOME`, каталог запуска и наличие `AGENTS.override.md`.

### 8.3. Claude Code

Для совместимости проектный `CLAUDE.md` может быть очень коротким:

```markdown
@AGENTS.md

## Claude Code

[Только специфичные настройки и процедуры Claude]
```

Современные версии Claude Code умеют читать `AGENTS.md` напрямую, но поведение зависит от версии и настройки Project instructions. Импорт `@AGENTS.md` проще сохранить как совместимый вариант. Для Windows это надёжнее символической ссылки.

Проверка в интерактивной сессии:

```text
/context all
```

В списке Memory files должны быть ожидаемые файлы. Затем задайте контрольный вопрос о версии и одном уникальном правиле.

### 8.4. Gemini CLI

По умолчанию используются `~/.gemini/GEMINI.md` и иерархические проектные `GEMINI.md`. Официальный способ задать другие имена:

```json
{
  "context": {
    "fileName": ["AGENTS.md", "GEMINI.md"]
  }
}
```

Если одновременно оставить `AGENTS.md` и `GEMINI.md` с импортом `AGENTS.md`, текст может загрузиться дважды. Выберите один вариант: либо список имён без импорта, либо стандартный `GEMINI.md` с импортом.

Проверка:

```text
/memory show
```

### 8.5. Обычные веб-чаты без доступа к файловой системе

Обычный чат не обязан видеть ваш локальный репозиторий. Для него собирается отдельный безопасный пакет:

```text
dist/web-studio/
├── START_HERE.md
├── AGENTS.md
├── STUDIO.md
└── CONTEXT.md
```

- ChatGPT Projects позволяет работать с проектными файлами и инструкциями. Официальная справка отдельно предупреждает: Google Drive app внутри Project не синхронизирует содержимое заранее ([ChatGPT Projects](https://help.openai.com/en/articles/10169521-using-projects-in-chatgpt)).
- Claude Projects имеет собственные инструкции и базу знаний; совместное использование проектов зависит от тарифа и типа рабочего пространства ([Claude Projects](https://support.anthropic.com/en/articles/9517075-what-are-projects)).
- Gemini Gems принимает инструкции и загруженные файлы знаний ([Gemini Gems](https://support.google.com/gemini/answer/15235603?hl=en)).

Обновление веб-проекта - новый управляемый экспорт, а не надежда, что старый загруженный файл сам обновился. В `START_HERE.md` ставьте версию, дату и список включённых документов.

### 8.6. Как обновлять файлы, не стирая локальные настройки

Синхронизатор не должен перезаписывать весь существующий файл. Используйте управляемый блок:

```markdown
<!-- AI-OS:BEGIN version=1.0.0 -->
[Сгенерированные общие правила]
<!-- AI-OS:END -->

[Локальные дополнения, которые синхронизатор не трогает]
```

Перед первым изменением создаётся резервная копия. Команда `sync --check` только показывает расхождение, `sync` предлагает diff, а запись выполняется после подтверждения. Для командных компьютеров допустим автоматический `sync --check` с падением CI при устаревании.

## 9. Как передавать знания между чатами и моделями

Передаётся не вся переписка, а проверенный результат работы. Полный чат содержит рассуждения, отвергнутые варианты, случайные секреты и устаревшие промежуточные состояния.

### В конце каждой содержательной сессии

1. Получите `git status` и зафиксируйте точный commit, если коммит разрешён.
2. Запишите реально изменённые файлы.
3. Вставьте результаты проверок, включая неуспешные и непроверенные участки.
4. Обновите `STATE.md`: этап, следующий шаг, блокеры.
5. Добавьте решение в `DECISIONS.md`, только если оно действительно принято.
6. Перепишите `HANDOFF.md` как последнюю актуальную передачу, без бесконечного наращивания.
7. Не переносите в общую память токены, персональные данные и полный вывод команд с чувствительными путями.

### Промпт для новой нейросети

```text
До любых изменений прочитай AGENTS.md, CONTEXT.md, docs/STATE.md,
docs/DECISIONS.md и docs/HANDOFF.md. Открой задачу [ссылка] в трекере.

Верни коротко:
1. Цель и область данных.
2. Текущий этап и последний проверенный commit.
3. Действующие решения.
4. Что уже проверено и каким способом.
5. Следующий шаг, блокеры и неизвестное.

Ничего не меняй. После этого жди моего подтверждения.
```

### Проверка, что знания действительно переданы

Задайте разным моделям одинаковые пять вопросов:

- Какова цель текущего этапа?
- Что является источником статуса задач?
- Какие три действия запрещены в этом проекте?
- Какая команда доказывает готовность?
- Что должно произойти после завершения сессии?

Правильный ответ недостаточен, если модель не может указать файл или запись, откуда он взят. При расхождении исправляется источник или адаптер, а не добавляется ещё один повторяющийся промпт.

## 10. Google Drive должен быть резервом, а не рабочей синхронизацией

Рабочая синхронизация - Git. Резерв - неизменяемые архивы с датой, commit hash, контрольными суммами и отдельным шифрованием.

### Схема 3-2-1

1. Локальная рабочая копия на компьютере.
2. Приватный удалённый Git-репозиторий с историей.
3. Шифрованный архив на Google Drive.

`git bundle` сохраняет историю Git, а `git archive` даёт удобный снимок файлов конкретного commit. Вместе они позволяют восстановиться даже без исходного GitHub.

### 10.1. Настройка rclone

[rclone Google Drive](https://rclone.org/drive/) поддерживает OAuth, Shared Drives, выбор корневой папки и service account для автономной работы. Документация на 25.11.2026 рекомендует собственный Google OAuth client ID, поскольку общий client ID rclone выводится из использования в 2026 году.

Порядок:

1. Создайте на Google Drive отдельную папку `ai-os-backup`.
2. Настройте remote через `rclone config`.
3. Используйте собственный OAuth client ID и минимально достаточные права.
4. Ограничьте remote нужной корневой папкой, если сценарий это позволяет.
5. Создайте поверх Drive remote тип `crypt`.
6. Пароли `crypt` и пароль конфигурации rclone храните отдельно в менеджере паролей и офлайн-восстановлении.
7. Не помещайте `rclone.conf`, OAuth JSON и пароли в Git или в сам архив.

[rclone crypt](https://rclone.org/crypt/) шифрует данные на клиенте до загрузки. Но пароль в обычном `rclone.conf` лишь слабо скрыт, поэтому нужна защита самой конфигурации. Потеря пароля и salt может сделать резерв невосстановимым.

### 10.2. Что отправляется

```text
Google Drive / ai-os-backup /
└── ai-personal/
    └── 2026-11-25T03-47-00Z/
        ├── ai-personal.bundle
        ├── ai-personal.tar.gz
        ├── manifest.txt
        └── SHA256SUMS
```

Дата в примере обозначает формат, а не обещание существующей копии. В `manifest.txt` записываются репозиторий, commit, время, версия схемы и версии инструментов. Секреты в manifest не попадают.

### 10.3. Каркас `backup.sh`

Это основа для реализации, которую нужно проверить в вашей среде перед расписанием:

```bash
#!/bin/bash
set -euo pipefail

repo="${1:?Укажи путь к репозиторию}"
remote="${AI_OS_REMOTE:?Укажи имя шифрованного rclone remote}"
name="$(basename "$repo")"
stamp="$(date -u +%Y-%m-%dT%H-%M-%SZ)"
tmp="$(mktemp -d)"
trap 'rm -rf "$tmp"' EXIT

cd "$repo"
test -d .git
git diff --quiet
git diff --cached --quiet
python3 scripts/validate.py
python3 scripts/build.py --check

commit="$(git rev-parse HEAD)"
bundle="$tmp/$name.bundle"
archive="$tmp/$name.tar.gz"

git bundle create "$bundle" --all
git bundle verify "$bundle"
git archive --format=tar.gz --output="$archive" "$commit"

{
  echo "repository=$name"
  echo "commit=$commit"
  echo "created_utc=$stamp"
  echo "schema_version=1"
} > "$tmp/manifest.txt"

(
  cd "$tmp"
  shasum -a 256 "$name.bundle" "$name.tar.gz" manifest.txt > SHA256SUMS
)

rclone copy "$tmp" "$remote/$name/$stamp" --checksum
rclone lsl "$remote/$name/$stamp/manifest.txt" >/dev/null
```

Почему `rclone copy`, а не `rclone sync`: каждый запуск создаёт новый каталог и не удаляет предыдущие копии. `sync` полезен для зеркала, но ошибочное удаление источника может превратиться в удаление резерва.

Скрипт останавливается при незакоммиченных изменениях. Это лучше, чем молча архивировать смесь старого commit и новых файлов. Черновики либо фиксируются отдельной веткой, либо архивируются другим явным режимом.

### 10.4. Хранение и восстановление

Рекомендуемая стартовая политика: 30 ежедневных копий, 12 еженедельных и 12 ежемесячных. Это настраиваемая политика, а не требование Google. Удаление старых архивов включается только после успешных тестов восстановления и отдельного ревью.

Проверка восстановления:

```bash
rclone copy "$AI_OS_REMOTE/ai-personal/ВЫБРАННАЯ_ДАТА" /tmp/ai-os-restore
cd /tmp/ai-os-restore
shasum -a 256 -c SHA256SUMS
git bundle verify ai-personal.bundle
git clone ai-personal.bundle restored
cd restored
python3 scripts/validate.py
```

Раз в месяц выполняйте реальное восстановление в пустой каталог и открывайте несколько ключевых файлов. Сообщение `rclone copy` без restore-теста не доказывает, что резерв пригоден.

### 10.5. Google Drive для команды

[Google Shared Drives](https://support.google.com/a/users/answer/7212025?hl=en) хранит файлы на уровне команды, а не отдельного сотрудника. После ухода человека файлы остаются у организации. Доступ внешних людей зависит от настроек организации.

Для студии полезны две разные области:

- рабочие документы команды - Shared Drive с ролями;
- автоматические архивы - отдельная ограниченная папка, куда агент только добавляет копии.

Не давайте ежедневному роботу право удалять всё на общем диске. Резервный сервисный аккаунт не должен быть владельцем рабочих документов.

## 11. Ежедневный агент состоит из робота и необязательной LLM-сводки

Для надёжности разделите детерминированные операции и рассуждение модели.

| Операция | Кто выполняет | Может ли LLM решать сама |
|---|---|---|
| `git pull --ff-only` | Скрипт | Нет |
| Проверка схемы и ссылок | Скрипт и CI | Нет |
| Сборка адаптеров | Скрипт | Нет |
| Сравнение версий и контрольных сумм | Скрипт | Нет |
| Создание и отправка архива | Скрипт | Нет |
| Проверка восстановления | Скрипт по расписанию | Нет |
| Объяснение ошибки человеку | LLM по журналу | Да, без изменения данных |
| Сводка задач и блокеров | LLM по свежим данным API | Да, с указанием источников |
| Изменение правил | Человек через PR | Нет |
| Закрытие задачи | Ответственный человек | Нет |
| Публикация и выпуск | Уполномоченный человек | Нет |

### 11.1. Ежедневный сценарий

Пример расписания: 06:47 НСК, до начала вашего дня. Конкретное время можно изменить.

1. Получить блокировку, чтобы два запуска не работали одновременно.
2. Проверить чистоту репозитория и выполнить `git pull --ff-only`.
3. Проверить версии схем, YAML, ссылки, лимиты и запрещённые файлы.
4. Запустить `build.py --check`: сгенерированные адаптеры не должны отличаться от исходников.
5. Проверить, что локальные установки содержат актуальный управляемый блок.
6. Создать Git bundle, снимок и контрольные суммы.
7. Отправить новый шифрованный архив на Google Drive.
8. Прочитать свежие задачи через API трекера.
9. Сформировать список просроченного, заблокированного, зависшего в ревью и лишённого следующего шага.
10. Сохранить технический отчёт и отправить короткое уведомление.
11. При ошибке остановиться с ненулевым кодом и сообщить, на каком шаге нет результата.

LLM можно вызвать после шага 9, чтобы превратить данные в понятную сводку. Если LLM недоступна, резерв и валидация всё равно должны завершиться.

### 11.2. Где запускать

| Место | Плюсы | Ограничения | Когда выбрать |
|---|---|---|---|
| Ваш Mac через `launchd` | Простой доступ к локальным проектам | Нужны включённый компьютер, доступ и аккуратный контроль памяти | Личный MVP |
| VPS через cron или systemd timer | Работает без вашего компьютера, отдельные лимиты | Нужны сервисные credentials и защита сервера | Постоянный вариант |
| GitHub Actions | Расписание и CI рядом с репозиторием | Задержки, секреты в Actions, лимиты и правила тарифа | Валидация и командный резерв |
| Сессия Kimi cron | Удобно для напоминания внутри чата | Работает только пока жива и свободна сессия, не переносится в новый чат | Не использовать как единственный резерв |

Для серьёзного ежедневного резерва лучше VPS или GitHub Actions, а не открытый чат. [Документация GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) предупреждает о задержках расписаний при высокой нагрузке. В публичных репозиториях расписание автоматически отключается после 60 дней без активности. Для критического процесса нужен контроль фактического последнего запуска.

### 11.3. Пример workflow для технической части

```yaml
name: ai-os-daily

on:
  schedule:
    - cron: '47 22 * * *'  # 06:47 НСК, UTC+7
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ai-os-daily
  cancel-in-progress: false

jobs:
  validate-and-backup:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-python@v5
        with:
          python-version: '3.13'

      - name: Validate sources
        run: python3 scripts/validate.py

      - name: Check generated adapters
        run: python3 scripts/build.py --check

      - name: Install rclone
        run: |
          curl -fsSL https://rclone.org/install.sh | bash

      - name: Configure rclone
        env:
          RCLONE_CONFIG_CONTENT: ${{ secrets.RCLONE_CONFIG_CONTENT }}
        run: |
          install -m 600 /dev/null "$RUNNER_TEMP/rclone.conf"
          printf '%s' "$RCLONE_CONFIG_CONTENT" > "$RUNNER_TEMP/rclone.conf"

      - name: Backup
        env:
          AI_OS_REMOTE: ai-os-crypt
          RCLONE_CONFIG: ${{ runner.temp }}/rclone.conf
          RCLONE_CONFIG_PASS: ${{ secrets.RCLONE_CONFIG_PASS }}
        run: ./scripts/backup.sh "$GITHUB_WORKSPACE"
```

Это архитектурный пример, а не готовый безопасный workflow. Перед эксплуатацией нужно закрепить версии actions и rclone, проверить формат секретной конфигурации, права токена, маскирование журналов и восстановление. Не печатайте `RCLONE_CONFIG` в лог.

### 11.4. LLM-агент и подписки

Не рассчитывайте, что обычную персональную подписку можно автоматически использовать как круглосуточный сервис. Для автономного агента выбирайте официально поддерживаемый API или headless-режим конкретного продукта, отдельный service account, бюджет и ограничение расхода.

Личные OAuth cookies и токены сотрудников на общий VPS не переносятся. Если LLM нужна только для сводки, начните с одного запуска в день и жёсткого лимита входных данных. Техническая часть вообще не требует модели.

### 11.5. Наблюдаемость

Минимальный журнал запуска:

```yaml
run_id: 2026-11-25T06-47-00+07:00
repository: ai-personal
commit: EXAMPLE
validation: passed
adapters: current
backup: uploaded
restore_test: not_scheduled
tasks_source: github_project
notification: sent
```

Отдельно контролируйте не только ошибку запуска, но и отсутствие запуска. Например, если успешного резерва нет больше 25 часов, создаётся предупреждение. Число 25 часов здесь - рекомендуемый стартовый порог для ежедневного процесса.

## 12. Команда может работать с разными подписками и компьютерами

Подписка на нейросеть и доступ к знаниям студии - разные вещи. Не нужно передавать сотруднику ваш аккаунт Kimi, Claude, ChatGPT или Gemini. Каждый использует свою подписку, а общий контекст получает через GitHub и настройки проекта.

### 12.1. Роли

| Роль | Правила студии | Код проекта | Задачи | Секреты и выпуск |
|---|---|---|---|---|
| Владелец студии | Утверждает | Полный по необходимости | Полные | Утверждает и владеет восстановлением |
| Maintainer | Предлагает через PR | Write по проекту | Меняет назначенные | Только выделенные сервисные доступы |
| Исполнитель | Читает | Ветки и PR | Меняет свои задачи | Нет по умолчанию |
| Внешний подрядчик | Только необходимый раздел | Только отдельный проект | Только свои задачи | Нет общих секретов |
| Агент резерва | Читает нужный репозиторий | Не меняет исходники | Не читает, если не нужно | Только ограниченный backup-доступ |
| Агент задач студии | Читает командные правила | Метаданные PR по необходимости | Читает и комментирует | Нет доступа к личному и прод-секретам |

Минимальный доступ важнее удобства «пусть всё видит». Уход сотрудника не должен требовать пересборки всей системы знаний.

### 12.2. Подключение нового члена команды

1. Добавьте его личный GitHub-аккаунт в нужную команду организации.
2. Выдайте доступ только к `studio-team` и нужным проектам.
3. Сотрудник клонирует репозитории на свой компьютер.
4. Он устанавливает адаптер для своей нейросети, не меняя чужие глобальные настройки.
5. Запускается `validate.py` и `sync.py --check`.
6. Новая сессия нейросети должна назвать версию правил, проект и критерий готовности.
7. Сотрудник получает одну задачу через трекер и проходит полный цикл PR.
8. Только после этого ему открывают дополнительные проекты.

### 12.3. Единый рабочий цикл

```text
Задача в трекере
  → ветка
  → работа любой нейросети
  → локальные проверки
  → обновление STATE и HANDOFF
  → pull request
  → CI и ревью
  → человеческое одобрение
  → merge
  → статус задачи и сводка
```

Нейросеть не является владельцем результата. Отвечает человек, который поставил задачу или принял изменение.

### 12.4. Защита общих правил от случайных изменений

[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) автоматически запрашивает ревью ответственных людей. Пример:

```text
/AGENTS.md                         @ORG/ai-governance
/STUDIO.md                         @ORG/studio-leads
/.github/workflows/                @ORG/ai-governance
/scripts/                          @ORG/ai-governance
/.claude/                          @ORG/ai-governance
/**/AGENTS.md                      @ORG/ai-governance
/**/REVIEW.md                      @ORG/ai-governance
```

`@ORG/...` нужно заменить реальными командами. Сам `CODEOWNERS` работает как обязательный барьер только вместе с защитой ветки и требованием ревью code owner.

Для `main` рекомендуется:

- запрет прямого push для агентов;
- обязательный pull request;
- обязательные проверки валидации и сборки;
- ревью владельца для правил, hooks, workflows и скриптов резерва;
- сброс устаревших одобрений после нового commit;
- запрет force push;
- при высоком риске применение правил также к администраторам.

Доступность отдельных функций на приватных репозиториях зависит от тарифа GitHub. Это проверяется на вашей организации до выбора схемы, а не предполагается заранее.

### 12.5. Конфликты и уход человека

При одновременном редактировании решается Git-конфликт через PR, а не выбирается «последний файл на Диске». Нельзя автоматически объединять противоречащие правила силами LLM.

При уходе сотрудника:

1. Отозвать доступ GitHub и Google.
2. Отозвать его персональные токены и сервисные ключи, если они выдавались.
3. Переназначить открытые задачи.
4. Проверить PR и изменения инструкций за последний период.
5. Сохранить рабочие документы в Shared Drive и Git.
6. Не удалять его личные чаты и не пытаться считать их корпоративной памятью.

## 13. Агент задач студии должен опираться на трекер, а не на свою память

Если у студии уже есть трекер, сохраните его как источник истины и подключите API. Если трекера нет, стартовый вариант - GitHub Projects с Issues, потому что задача, ветка, PR и проверки оказываются рядом.

### 13.1. Модель задачи

| Поле | Обязательность | Зачем |
|---|---|---|
| `id` и ссылка | Обязательно | Однозначная идентификация |
| `scope` | Обязательно | `studio-team` или `studio-private` |
| `project` | Обязательно | К какому проекту относится |
| `owner` | Обязательно после назначения | Один ответственный |
| `status` | Обязательно | Текущее состояние |
| `priority` | Обязательно в работе | Порядок выбора |
| `due` | Когда срок реально существует | Контроль просрочки |
| `next_action` | Обязательно для активной | Что сделать физически следующим действием |
| `blocker` | Для заблокированной | Что и кто должен разблокировать |
| `acceptance` | Обязательно | Как доказывается результат |
| `evidence` | Для ревью и завершения | Ссылки на тест, PR, запрос или артефакт |
| `updated_at` | Автоматически | Поиск зависших задач |

Не нужно переносить всю эту таблицу в `STATE.md`. Проектное состояние содержит ссылку на активную задачу и общий этап.

### 13.2. Статусная машина

```text
inbox → ready → in_progress → review → done
           ↑         │             │
           └──── blocked ←─────────┘
                       ↓
                    canceled
```

Практические правила:

- `inbox` может не иметь владельца, но должна быть разобрана;
- `ready` содержит результат, владельца и критерий приёмки;
- `in_progress` имеет одно следующее действие;
- `blocked` содержит конкретный блокер и ответственного за разблокировку;
- `review` содержит доказательства;
- `done` подтверждает человек после приёмки;
- новый существенный объём работы - новая задача, а не бесконечное продление старой.

Агент может предложить переход в `review`, если появились заданные доказательства. Он не должен сам переводить в `done`.

### 13.3. Шаблон Issue

```markdown
## Результат

[Что должно измениться одной фразой]

## Область и проект

- Scope: studio-team
- Project: [id]
- Owner: [логин]
- Due: [дата или «нет внешнего срока»]

## Следующее действие

[Конкретный шаг]

## Нельзя менять

[Границы]

## Готово, когда

[Команда, реальный сценарий и ожидаемый результат]

## Доказательства

[PR, вывод проверки, артефакт]

## Блокеры

[Что мешает]
```

### 13.4. Права агента задач

Минимальный стартовый набор:

- читать задачи `studio-team`;
- читать связанные PR и статусы CI;
- добавлять комментарий со сводкой;
- ставить предложенную метку `needs-attention`;
- создавать черновик ежедневного отчёта.

Не выдавайте на старте:

- доступ к `ai-personal`;
- доступ к финансам и договорам `studio-private`;
- право менять чужие статусы без журнала;
- право закрывать задачи;
- право менять правила и CI;
- доступ к production-секретам.

### 13.5. Что агент сообщает каждый день

```text
Сводка студии на [дата, часовой пояс]

Требуют вашего решения:
- STU-124: блокер [причина], ответственный [человек], не обновлялась [по данным API].

Просрочено:
- [Задача, срок, владелец, следующее действие]

Зависло без обновления:
- [Задача, статус, последнее событие]

Ожидает ревью:
- [Задача, PR, состояние проверок]

Завершено и принято людьми за период:
- [Задача, ссылка на результат]

Данные: [ссылка на Project и время запроса].
Непроверенное: [какие источники были недоступны].
```

Агент не пишет «всё спокойно», если API одного проекта вернул ошибку. Он отмечает пробел в данных.

### 13.6. Ежедневно и по событиям

Ежедневного запуска достаточно для сводки и резерва. Но статус задачи лучше обновлять сразу по событию:

- PR открыт - задача может перейти в `review` после проверки правил;
- проверка упала - комментарий о блокере;
- PR merged - ожидание человеческой приёмки;
- Issue закрыт человеком - `done`.

События обрабатываются webhook или CI. Ежедневный запуск затем сверяет расхождения и исправляет только отчёты, не переписывая историю.

### 13.7. Маршрутизация личного и студийного

Используйте два отдельных агента или два изолированных профиля:

| Профиль | Источники | Токен | Кому доступен |
|---|---|---|---|
| Личный ассистент | `ai-personal` и выбранные личные задачи | Ваш личный, без командной публикации | Только вы |
| Агент студии | `studio-team` и командный Project | Сервисный аккаунт организации | Команда по ролям |
| Приватный агент студии | `studio-private` | Отдельный, ограниченный | Только допущенные |

Общий интерфейс может задавать вопрос «куда отнести?», но исполнение должно идти через разные credentials. Один агент с доступом ко всем репозиториям может случайно использовать личный контекст в командном ответе.

## 14. Правила становятся защитой только на четырёх уровнях

| Уровень | Пример | Что доказывает |
|---|---|---|
| Текст | «Не публикуй без разрешения» | Намерение, но не гарантию |
| Клиент | Permission deny и `PreToolUse` hook | Запрет конкретного вызова в конкретной среде |
| Репозиторий | CI, CODEOWNERS, protected branch | Невозможность обычного merge без условий |
| Внешний сервис | Минимальные роли, отдельный service account, запрет публикации | Даже скомпрометированный агент не имеет лишней власти |

### 14.1. Как перенести восемь запретов статьи в общую систему

| Риск | Локально | Серверно |
|---|---|---|
| Обход проверок | Запрет опасных флагов | Обязательные проверки от доверенного CI |
| Потеря незакоммиченной работы | Политика на destructive Git по проекту | Регулярные ветки и резерв |
| Force push | Вопрос или запрет | Запрет на защищённой ветке |
| Случайный commit чужого | Явные пути и проверка diff | CODEOWNERS и ревью |
| Чтение `.env` | Deny для Read, Bash и других инструментов | Секреты вне репозитория, секрет-менеджер |
| Самовольный выпуск | Локальный запрет помогает | Права deploy только у доверенной роли |
| Изменение самой защиты | Вопрос человеку | CODEOWNERS и обязательное ревью |

Не пытайтесь написать универсальный shell-regex на все команды. Составные команды, алиасы, другие инструменты и разные ОС делают это сложным. Для критичных вещей убирайте само разрешение, а не только распознавайте опасную строку.

### 14.2. Инструкции тоже могут быть вредоносными

Файл `AGENTS.md` из чужого репозитория - данные с высоким влиянием на агента. В него можно внести инструкцию раскрыть секрет или отключить проверку. Поэтому:

- изменения инструкций проходят то же ревью, что и security-код;
- внешний контент не может отменить ваши верхнеуровневые правила;
- агент не выполняет команды из случайных документов без проверки;
- web-страница, issue и комментарий PR не являются разрешением на опасное действие;
- агент сообщает, какой источник инструкций загружен.

### 14.3. Что никогда не входит в общий файл

- API keys, OAuth tokens, cookies и приватные ключи;
- содержимое `.env`;
- пароли от rclone и salt в открытом виде;
- полные клиентские базы;
- личные данные сотрудников без необходимости;
- необработанные диагностические архивы сессий;
- секретные URL и токены в query string.

Для проверки добавьте secret scanning и CI-правила на типичные секретные файлы. Но автоматический сканер не заменяет разграничение доступа.

## 15. Внедрять нужно этапами с проверкой после каждого

Не начинайте с автономного агента. Сначала докажите, что знания можно восстановить вручную.

### Этап 0. Инвентаризация

**Сделать:** список нейросетей, компьютеров, проектов, существующих правил, трекеров, владельцев и областей данных.

**Результат:** одна таблица и решение, что является источником истины для каждого типа данных.

**Проверка:** ни один существующий файл не удалён, ничего не опубликовано.

### Этап 1. Личный MVP

**Сделать:** `ai-personal`, короткий `AGENTS.md`, один проектный `CONTEXT.md`, `STATE.md`, `DECISIONS.md` и `HANDOFF.md`.

**Результат:** новый чат в двух разных инструментах правильно пересказывает проект без старой переписки.

**Проверка:** пять контрольных вопросов и одна реальная задача.

### Этап 2. Адаптеры

**Сделать:** генерацию `CLAUDE.md`, Codex, Gemini и Kimi; версию `AI_OS_VERSION`; команду `sync --check`.

**Результат:** обновление одного исходника предсказуемо появляется во всех выбранных инструментах.

**Проверка:** старая версия обнаруживается, локальные дополнения не стираются, нет двойного импорта.

### Этап 3. Резерв

**Сделать:** rclone, шифрование, Git bundle, manifest и ручное восстановление.

**Результат:** репозиторий восстановлен в пустой каталог только из Google Drive и офлайн-ключей.

**Проверка:** контрольные суммы, `git bundle verify`, клонирование и `validate.py`.

### Этап 4. Студия и задачи

**Сделать:** `studio-team`, классификацию, GitHub Project или адаптер текущего трекера, шаблон Issue.

**Результат:** команда видит только командное, у каждой активной задачи есть владелец и следующее действие.

**Проверка:** тестовый сотрудник не видит личные и приватные репозитории; агент получает статусы из API.

### Этап 5. Командная защита

**Сделать:** CODEOWNERS, защищённые ветки, обязательный CI, роли и процедуру offboarding.

**Результат:** изменение `AGENTS.md` или workflow нельзя влить без назначенного ревью.

**Проверка:** отдельный тестовый PR пытается изменить защиту и останавливается.

### Этап 6. Ежедневная автоматика

**Сделать:** сначала скрипты без LLM, затем уведомления, затем необязательную LLM-сводку.

**Результат:** ежедневный резерв и отчёт идут без открытого чата.

**Проверка:** ручной запуск, запуск по расписанию, повторный запуск, ошибка сети, недоступность LLM и предупреждение об отсутствии резерва.

### Этап 7. Агент задач

**Сделать:** read-only интеграцию, ежедневную сводку, затем комментарии и события.

**Результат:** агент показывает реальные статусы и источники, но не принимает работу за человека.

**Проверка:** закрытие задачи человеком, ложный PR без доказательств, ошибка API и попытка доступа к личному проекту.

## 16. Приёмочные испытания всей системы

### 16.1. Переносимость

- На чистом компьютере клонируются только разрешённые репозитории.
- Установщик показывает diff и не стирает локальные правила.
- Kimi, Codex, Claude и Gemini называют одну версию общего пакета.
- Новый чат без старой истории находит цель, этап, решения и следующий шаг.
- Изменение одного исходника обнаруживается всеми адаптерами.

### 16.2. Резерв

- Ежедневный запуск создаёт новый каталог и не удаляет предыдущий.
- Повторный запуск не создаёт конфликт и не работает параллельно с первым.
- Повреждение архива обнаруживается контрольной суммой.
- Восстановление выполнено на другой машине или в чистом каталоге.
- Без пароля восстановления зашифрованные данные не читаются.
- Пароль восстановления не хранится только на том же компьютере и только в том же архиве.

### 16.3. Команда

- Сотрудник со своей подпиской получает тот же проектный контекст.
- Подрядчик не видит другие клиенты и личные данные.
- PR на `AGENTS.md`, hooks и workflows требует назначенного владельца.
- Force push и merge без проверок останавливаются сервером.
- После отзыва доступа сотрудник теряет и Git, и Shared Drive по регламенту.

### 16.4. Задачи

- Агент различает `personal`, `studio-private` и `studio-team`.
- Любая цифра сводки имеет время и ссылку на источник.
- Ошибка API отображается как «нет данных», а не как ноль задач.
- Агент не переводит задачу в `done` без человека.
- Просроченная и заблокированная задача попадает в сводку.
- Личная задача не попадает в командный отчёт.

### 16.5. Безопасность

Проверяются разные способы, а не только очевидная shell-команда:

- чтение секрета через `Read`;
- чтение через `Bash`;
- копирование секрета в разрешённый файл;
- внешняя отправка через MCP или сетевой инструмент;
- изменение локального hook;
- изменение workflow в PR;
- merge без актуального одобрения.

Если хотя бы один критический путь открыт, формулировка «защищено» преждевременна.

## 17. Метрики полезности, а не количество файлов

Раз в неделю достаточно смотреть на несколько показателей:

| Метрика | Хороший сигнал |
|---|---|
| Доля проектов со свежим `STATE.md` | Активные проекты обновляются после проверенных шагов |
| Число противоречий адаптеров | Стремится к нулю |
| Последний успешный restore-тест | Есть фактическая дата и результат |
| Активные задачи без владельца | Нет, кроме сознательно разбираемого inbox |
| Активные задачи без следующего действия | Нет |
| Задачи, зависшие без событий | Видны и разбираются |
| Исправления прошлой ошибки | Снижаются со временем |
| Ложные блокировки защиты | Разбираются, правило сужается без отключения всей защиты |
| Утечки между областями | Недопустимы |

Красивое число hooks или размер базы знаний само по себе ничего не доказывает. Важны восстановление, актуальность и уменьшение повторных ошибок.

## 18. Компромиссы и стоимость владения

### Git вместо одного файла на Диске

**Плюс:** история, ревью, роли, восстановление и совместимость с кодом.

**Минус:** команде нужно освоить простой PR-процесс. Для нетехнических сотрудников можно дать форму задачи и веб-редактор GitHub, не требуя изучения всего Git.

### Три области вместо одного монорепозитория

**Плюс:** реальная конфиденциальность и независимый offboarding.

**Минус:** больше репозиториев и аккуратнее навигация. Реестр и единые шаблоны снижают сложность.

### Два агента вместо одного всезнающего

**Плюс:** личное не смешивается с командным, токены разделены.

**Минус:** нужно маршрутизировать запросы. Начните с двух явных команд или чатов, не стройте автоматический роутер до появления реальной необходимости.

### Робот плюс LLM вместо полностью автономного ИИ

**Плюс:** резерв не зависит от галлюцинации и доступности модели.

**Минус:** нужны обычные скрипты и их сопровождение. Зато их можно тестировать.

### Ожидаемые расходы

Точную смету можно дать только после выбора GitHub-тарифа, Google Workspace, VPS и LLM API. Отдельно учитываются:

- приватные репозитории и функции защиты веток;
- место на Google Drive;
- небольшой VPS при выборе постоянного запуска;
- API-запросы для сводок;
- время на первичную инвентаризацию и еженедельное ревью.

Не покупайте командные тарифы всех нейросетей только ради общего файла. Общий Git-слой работает независимо от того, какая модель у сотрудника.

## 19. Итоговая рекомендуемая конфигурация

Если свести весь документ к одному решению, я рекомендую именно это:

1. **Ваш общий файл:** `~/.agents/AGENTS.md`, собранный из `ai-personal`. Он короткий и содержит стартовый протокол.
2. **Специфика инструментов:** небольшие `~/.kimi-code/AGENTS.md`, `~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md` и `~/.gemini/GEMINI.md` без копирования всей базы.
3. **Проект:** корневой `AGENTS.md`, рядом `CONTEXT.md`, а в `docs/` файлы `STATE.md`, `DECISIONS.md`, `HANDOFF.md`.
4. **Ревью:** общий раздел ревью в `AGENTS.md`, адаптер `REVIEW.md` только для Claude Code Review, человеческие правила в CODEOWNERS и protected branches.
5. **Студия:** отдельные `studio-private` и `studio-team`; личное в командный Git не попадает.
6. **Задачи:** один существующий трекер либо GitHub Projects. Агент задач имеет read-only старт и не закрывает работу за человека.
7. **Синхронизация:** приватный Git, адаптеры с версией и `sync --check` на каждом компьютере.
8. **Google Drive:** ежедневный Git bundle плюс архив, manifest, SHA-256 и rclone crypt. Рабочие файлы команды могут лежать в Shared Drive, но не заменяют Git.
9. **Ежедневный процесс:** VPS или GitHub Actions для робота, Mac `launchd` как личный MVP. LLM только объясняет и суммирует.
10. **Запуск:** семь этапов с приёмкой, без одновременной автоматизации всей студии.

## 20. Что нужно от вас для фактического внедрения

Сейчас подготовлено решение и шаблоны. Чтобы превратить его в работающую систему, нужны следующие решения и доступы:

- список ваших нейросетей и компьютеров, которые входят в первый этап;
- один проект для пилота;
- подтверждение четырёх областей и владельцев доступа;
- выбранный трекер задач студии;
- GitHub-организация или решение начать только с личного приватного репозитория;
- папка Google Drive и способ выдачи ограниченного доступа rclone;
- место запуска: Mac, VPS или GitHub Actions;
- отдельное разрешение на внешнюю публикацию любых реальных правил и контекстов.

Секреты заранее присылать в чат не нужно. На этапе настройки они вводятся в системный менеджер секретов или через официальный OAuth-процесс.

## 21. Что раскрыть следующим шагом

- Реализовать `build.py`, `validate.py` и `sync.py --check` под ваш фактический набор инструментов.
- Собрать первый `AGENTS.md` из существующих правил без потери и дублирования.
- Настроить адаптеры и провести пять одинаковых испытаний на разных моделях.
- Реализовать `backup.sh`, затем доказать восстановление на чистой машине.
- Подключить API вашего реального трекера и определить права агента задач.
- Настроить защищённые ветки и CODEOWNERS на конкретном GitHub-тарифе.
- Только после этого включать ежедневное расписание и LLM-сводки.
